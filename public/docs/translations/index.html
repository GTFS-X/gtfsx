Translations

In regions with more than one official or widely spoken language, riders expect stop names, route names and headsigns in their own language. GTFS carries those in translations.txt, and GTFS·X edits it for you: translate a single stop, route or agency from its own panel, or manage every translation in the feed from the Translations section. It’s free on every plan.

Turn translations on

Translations is an advanced feature, off by default so the editor stays simple for single-language feeds. Turn it on in Settings (the gear in the left rail) → Translations. If you import a feed that already has a translations.txt, it switches on by itself.

Once it’s on you get a Translations section under Setup in the left rail, and a Translations box at the bottom of the agency, route and stop panels.

Feed language and default language

Two settings in feed_info.txt tell apps how to read your translations. Both are in Agency → Feed Info, and repeated at the top of the Translations section:

  • Feed language (feed_lang) — the language your original names are written in, such as en. If the original text mixes languages (a Swiss feed with “Genève” and “Zürich” side by side), use mul and give a translation for every language.
  • Default language (default_lang, optional) — what apps show a rider whose language they don’t know. Usually your main language.

Languages are IETF BCP 47 codes: es for Spanish, fr-CA for Canadian French, zh-Hant for Traditional Chinese. The language picker suggests common codes, shows the language name as you type, and accepts any valid code.

Translating a stop, route or agency

Open the stop, route or agency and scroll to Translations. Click + Add language, pick the language, and type the translated name. Each translatable field gets a box, with the original text as a hint:

  • Stops — name, text-to-speech name, description, stop URL.
  • Routes — short name, long name, description, route URL.
  • Agency — name, URL, fare URL, phone, email. The agency needs an Agency ID, because translations refer to it by ID.

Leave a box empty to skip that field. Clearing a box deletes that translation, and Remove deletes a language’s translations for that record.

Headsigns: translate by value

The route panel also has Headsign translations, with one box per headsign used on the route. These are written by value: translating “Northbound” as “Hacia el norte” covers every trip whose headsign is exactly “Northbound”, including trips you add later. That’s how most multilingual feeds handle headsigns, and it saves translating hundreds of trips one by one.

The Translations section

The Translations section in the left rail lists every row in translations.txt. Filter by language or by table, or search the text. Click a row to edit it, or + Add to create one. That’s also where to translate things without their own panel, such as stop headsigns, trip short names, level names, pathway signs and feed contact details.

Each translation names what it translates in one of two ways, matching the spec:

  • One record — a field on one stop, route, trip, agency, level or pathway (record_id). A stop headsign also needs the stop’s position in the trip (record_sub_id, the stop_sequence).
  • Every matching value — the field everywhere it has exactly this text (field_value). The match has to be exact; a partial match isn’t translated.

Feed info translations use neither, because a feed has a single feed info row. If both kinds of translation cover the same value, the one-record translation wins.

Renames and deletions

Translations follow the records they belong to. Rename an agency ID, trip ID, level or pathway and its translations move with it. Delete a stop, route, trip, agency, level or pathway and its translations go too, and undo brings them back. By-value translations are left alone, because they name text rather than a record.

What validation checks

Translation problems show up in Validation as warnings, one line per kind of problem with a count and examples. They never block an export:

  • Left out of the export: translations that point at a record that doesn’t exist, use an invalid language code, repeat another row, break the record/value rules above, or translate the feed publisher (GTFS·X always publishes the feed as GTFS·X). They stay in the editor so you can fix them, and the Remove fix deletes them in one click.
  • Kept, with a note: translations of a table or field outside the spec, of a field that shouldn’t be translated (an ID or a color), or by-value translations whose text no record currently has. That last one usually means the original name was edited after it was translated.
  • Languages: a feed with translations but no feed language, an invalid feed or default language code, a default language with no translations in it, and mul with no translations.

Import and export

Importing a feed brings in its translations.txt row for row, including rows GTFS·X can’t resolve, so nothing is silently dropped. Exporting writes translations.txt only when the feed has translations. The spec’s optional columns appear only when a row uses them.

Translations of attributions.txt are kept in the editor but not exported, because GTFS·X doesn’t carry attributions.txt itself.
